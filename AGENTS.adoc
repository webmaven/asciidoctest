= developer handbook: asciidoctest Agent Guidelines
:toc: left

This document acts as an engineering handbook and guideline for agentic coding assistants maintaining and extending `asciidoctest`.

== Codebase Architecture

`asciidoctest` is designed to collect, parse, and execute Python code blocks from AsciiDoc (`.adoc`) files and Python docstrings. It acts as a bridge between AST-level AsciiDoc parsers and Python execution environments (both `pytest` and `unittest`).

=== Component Overview

[mermaid]
----
graph TD
    A[Source Files: .adoc, .py] --> B[pytest_plugin / unittest_integration]
    B --> C[parser.py]
    C --> D[asciidoctrine / asciidocstring]
    D --> E[TestBlock List]
    E --> F[runner.py]
    F --> G[CustomDocTestRunner / exec]
----

* **`parser.py`**: Extracts test blocks using `asciidoctrine` (for standalone documents) and `asciidocstring` (for Python docstrings). Supports `explicit` (default) and `eager` matching.
* **`runner.py`**: Coordinates execution. Interactive prompts are evaluated via `doctest.DocTestParser` and a custom `doctest.DocTestRunner` subclass. Non-interactive blocks are compiled and run via `exec()`. State is shared sequentially top-to-bottom across consecutive blocks inside a single standalone document.
* **`pytest_plugin.py`**: Discovers files statically, collects docstrings from Python modules without executing code during discovery, and handles test execution and error formatting for `pytest`.
* **`unittest_integration.py`**: Wraps test collection and execution in standard library `unittest.TestSuite` adapters (`DocFileSuite` and `DocTestSuite`).

---

== Core Design Principles

1. **AST-Based Extraction**: Never use regular expressions to parse block delimiters or document structures. Always rely on the AST generated by `asciidoctrine` and `asciidocstring`.
2. **Sequential Shared State**: Consecutive code blocks inside a standalone `.adoc` file are expected to share execution state sequentially. Maintain a single `shared_globals` dictionary for the lifetime of a document's run.
3. **No Code Execution during Discovery**: When pytest or unittest runs discovery, do not import or run modules. Use static AST parsing (via `ast.parse`) in `pytest_plugin.py` to identify docstrings that contain tests first.
4. **Understated & Demonstrative Documentation**: Keep all documentation objective and demonstration-focused. Avoid claiming "high developer experience" or similar marketing terms; demonstrate clarity through clean examples and explicit code blocks.

== Testing and Coverage

The test suite is structured to achieve maximum coverage and prevent regressions:

* **`tests/test_runner.py`**: Validates the sequential runner, state-sharing across interactive/non-interactive blocks, and standard exception propagation.
* **`tests/test_plugin.py`**: Basic pytest collection and integration tests.
* **`tests/test_plugin_coverage.py`**: Advanced pytest integration tests utilizing the `pytester` fixture to test error boundaries (unparseable AsciiDoc collection, syntax errors in python files, imported objects filter, and repr-failure fallbacks).
* **`tests/test_unittest_integration.py`**: Validates standard library `unittest` adapters, nested routines, duplicate discoveries, and class formatting.
* **`tests/test_footnotes.py`**: Verifies compatibility with the latest footnote macros (`footnote:[...]`, `footnoteref:[...]`) introduced in `asciidoctrine>=0.1.0a7`.

=== Coverage Validation
To get a full and accurate coverage report including pytest startup plugin registration, execute the test suite directly via `coverage`:

[source,bash]
----
.venv/bin/coverage run -m pytest
.venv/bin/coverage report -m
----

== Pre-Release Checklist

Always run through this checklist completely before tagging or uploading a new package release:

=== 1. Dependency Audit
* [ ] Verify that constraints in `pyproject.toml` are correctly aligned with the latest stable dependency releases.
* [ ] Ensure `asciidocstring` points to stable pre-release/release versions (e.g. `>=0.1.0a2`), avoiding premature or yanked releases.

=== 2. Code Quality and Style
* [ ] Format code using standard code style checkers.
* [ ] Run static type checking (e.g. `mypy`) to ensure type-safety across all modules.

=== 3. Verification Suite
* [ ] Install the package in editable mode with test dependencies:
  [source,bash]
  ----
  .venv/bin/pip install -e ".[test]"
  ----
* [ ] Run the complete test suite:
  [source,bash]
  ----
  .venv/bin/pytest
  ----
* [ ] Measure code coverage and confirm that coverage remains above 95% total:
  [source,bash]
  ----
  .venv/bin/coverage run -m pytest
  .venv/bin/coverage report
  ----

=== 4. Documentation Check
* [ ] Confirm that all examples inside `README.adoc` pass successfully under our self-verifying test suite.
* [ ] Update `CHANGELOG.adoc` to catalog the latest changes, additions, and fixed bugs under the appropriate release version header.

=== 5. Publishing Preparation
* [ ] Update the `version` field in `pyproject.toml`.
* [ ] Run build checks to generate clean source and wheel distributions:
  [source,bash]
  ----
  .venv/bin/python3 -m build
  ----
